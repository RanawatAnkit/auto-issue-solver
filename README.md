# Auto-Solver

Auto-Solver takes a GitHub issue and tries to fix it. It clones the repository, works out what
the issue is asking for, finds the code involved, plans a small change, edits the files,
runs the repository's tests in a Docker sandbox, repairs the change if tests fail, and
— only when tests pass — opens a pull request for a human to review.

It also includes a SWE-bench harness, so you can measure how often the agent actually fixes
real bugs from real projects, graded by the maintainers' own tests.

This is a final-year project, not a product. It works end to end, but a 7B local model solves
few real-world issues; the point is a pipeline that is honest about what it did and why it
stopped.

## How a run works

```
GitHub webhook (issue opened)  or  dashboard "Solve"
   │
   ▼
FastAPI ── Redis queue ──► worker (one process)
                              │
   clone the repo at the default branch, list git-tracked files
   index the code in pgvector (best effort; lexical search covers failures)
   IssueAnalyzer   LLM → problem, expected/current behaviour, likely files
   ContextBuilder  named files + semantic search + keyword search over the checkout
   PlannerAgent    LLM → files to change; every path is checked against the repo
                   ── stops here (PLAN_READY) unless ENABLE_CODE_MUTATION=true
   baseline tests  on the untouched checkout, in Docker, no network
                   ── stops if the sandbox cannot run this repo's tests at all
   CodingAgent     one file per LLM call, as search/replace or whole-symbol edits;
                   each edit is dry-run validated (unique match, valid syntax, in scope)
                   and retried with the concrete rejection reason
   tests  ──fail──► repair loop: analyze failure → plan → edit → re-test
                   (bounded by attempts, time, and "same failure twice")
   validate the real git diff (only planned files, secret scan)
   branch → commit → push → pull request
                   ── skipped (COMPLETED) when ENABLE_PR_CREATION=false
```

Every step is logged on the run (`GET /agent-runs/{id}/actions`) and shown in the dashboard.
A run only reaches `PR_CREATED` when the sandbox tests actually passed.

## SWE-bench evaluation

`backend/app/eval/` is a harness for a 32-task subset of
[SWE-bench Lite](https://www.swebench.com/): real issues from `psf/requests`, `pallets/flask`,
`pytest-dev/pytest` and `pylint-dev/pylint`, with their real base commits, problem statements
and hidden tests. The dataset file is generated by `backend/scripts/build_swebench_subset.py`.

For each task the harness:

1. checks the repository out at `base_commit` (repos are cached in `backend/.eval_cache/`);
2. runs the same analyzer → planner → coding agent as the production worker, giving it only the
   problem statement and the checkout, and takes `git diff` as the agent's patch;
3. applies that patch to a clean checkout, resets the test files touched by the maintainers'
   `test_patch`, and applies it;
4. builds a Docker image for the task's Python version and pinned dependencies, installs the
   repo, and runs the test files with `pytest -rA`;
5. grades the log with SWE-bench's rules: resolved only if every `FAIL_TO_PASS` test now passes
   and no `PASS_TO_PASS` test fails.

Results are split into outcomes, because a failure is only meaningful if the agent was given a
fair attempt:

| Outcome | Meaning | Counts against the agent? |
|---|---|---|
| `RESOLVED` | all required tests pass | — |
| `UNRESOLVED` | patch was tested, some required tests fail (or time out) | yes |
| `NO_PATCH` | no valid plan, edits rejected, or nothing changed | yes |
| `PATCH_APPLY_FAILED` | patch does not apply to a clean checkout | yes |
| `LLM_ERROR` | provider quota, bad key/model, outage | no |
| `ENV_ERROR` | Docker/install failure, or network needed but not allowed | no |
| `HARNESS_ERROR` | bug in the harness | no |

The dashboard and `python -m app.eval report` show both the strict rate (resolved / all tasks)
and the rate over attempted tasks. A quota or authentication error stops the batch instead of
recording the same failure 30 times.

**Gold validation.** `python -m app.eval validate` grades the maintainers' own fix; 31 of the
32 tasks validate in this harness (`pylint-dev__pylint-7080` cannot: one of its expected test IDs
contains an absolute path from the original environment). If the
reference fix does not pass, the environment is wrong and the task cannot say anything about
the agent. Run it before trusting any agent number; see [RUNGUIDE.md](RUNGUIDE.md).

## LLM providers

Set `LLM_PROVIDER` to one of:

- `ollama` — local and free. Default model `qwen2.5-coder:7b`. Uses Ollama's native
  schema-constrained JSON output; prompts are sized to `OLLAMA_NUM_CTX` before sending.
- `gemini` — through Google's OpenAI-compatible endpoint (`GEMINI_API_KEY`, `GEMINI_MODEL`).
- `openai` — `OPENAI_API_KEY`, `OPENAI_MODEL`.

An optional fallback provider is used only for quota errors (or outages, with
`LLM_FALLBACK_ON=unavailable`), and never to a paid provider unless `LLM_ALLOW_PAID_FALLBACK=true`.

## Configuration

Everything is read from the repository-root `.env` (template: `.env.example`). The ones you
will touch most:

| Variable | Default | Purpose |
|---|---|---|
| `LLM_PROVIDER` | `ollama` | which model answers |
| `ENABLE_CODE_MUTATION` | `false` | `false` stops after planning; nothing is changed |
| `ENABLE_PR_CREATION` | `true` | `false` verifies locally and never pushes |
| `MAX_REPAIR_ATTEMPTS` | `3` | repair loop bound |
| `TEST_TIMEOUT_SECONDS` | `300` | worker sandbox test timeout |
| `EVAL_TEST_TIMEOUT_SECONDS` | `1800` | per-task test timeout in the harness |
| `EVAL_RESULTS_DIR`, `EVAL_CACHE_DIR` | `backend/eval_results`, `backend/.eval_cache` | harness output and repo cache |
| `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY` | — | GitHub App (path to the `.pem`, kept out of git) |
| `GITHUB_WEBHOOK_SECRET` | — | webhooks are rejected until set |
| `GITHUB_OAUTH_CLIENT_ID/SECRET` | — | dashboard login |

## Getting started

[RUNGUIDE.md](RUNGUIDE.md) has the step-by-step setup, every command, and troubleshooting. Short
version, from the repo root on Windows (use `source venv/bin/activate` on Linux/macOS):

```bash
docker compose up -d                          # PostgreSQL + Redis
docker build -t test-sandbox:latest sandbox   # worker test sandbox
cd backend
python -m venv venv && venv\Scripts\activate
pip install -r requirements.txt
alembic upgrade head
pytest -q                                     # ~1 min, no services needed
uvicorn app.main:app --reload --port 8000     # API
python -m app.workers.issue_worker            # worker (second terminal)
cd ../frontend && npm install && npm run dev  # dashboard on :5173
```

Evaluate without the dashboard:

```bash
cd backend
python -m app.eval validate --repo pallets/flask      # check the environments first
python -m app.eval run pallets__flask-4045            # one task
python -m app.eval run --allow-network                # everything (requests tests need network)
python -m app.eval report
```

## Development

- Backend tests: `cd backend && pytest -q`. They use a throwaway SQLite database and never touch
  your dev database. Tests needing Postgres, Docker or a live Ollama skip with a printed reason.
- Frontend: `cd frontend && npm run lint && npm run build` (lint allows zero warnings).
- No Python linter or type checker is configured yet.
- Keep changes small and tested. Agent behaviour is easy to break silently; when you change a
  prompt or the patcher, run a few harness tasks before and after.
- Never commit `.env`, `.pem` files or harness output (all are in `.gitignore`).

## Limitations

- **Small models solve few real issues.** With `qwen2.5-coder:7b` on a 6 GB laptop GPU, the
  Flask tasks got through analysis and planning (~30 s each) but code generation degenerated:
  the model repeated the same lines until the 4096-token output limit (~8 minutes per attempt),
  ending in `NO_PATCH` or an Ollama timeout (`LLM_ERROR`). Bounding the edit lists in the schema
  stopped repeated *edits*, but not repetition inside one edit. Expect useful numbers only from a
  stronger model.
- **The harness does not run the repair loop.** It grades a single analyze → plan → code pass.
  The worker's repair loop needs a test environment for the target repo, which for benchmark
  repos means the harness's Docker images; wiring that in is the next step.
- **Only pytest-based repositories** are supported, by both the worker's sandbox and the harness
  (Node `npm test` works in the worker only). Django and SymPy from SWE-bench are not included.
- **Old `requests` tasks need the network** (they call httpbin.org), so they are graded only with
  `--allow-network`, and httpbin flakiness can make results noisy.
- **Single process state.** One worker, one evaluation job per API process, OAuth state in memory.
  Restarting the API abandons a running evaluation (recorded results are kept).
- The dashboard's GitHub login checks who you are, not your permissions on a repository: anyone
  who can log in can connect any repo the App is installed on that nobody else has claimed.
